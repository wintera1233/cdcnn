# GPU fault, 2026-09-21, and the pinned container

## What happened

The v6.9 epoch-aligned run
(`runs/20260921T014945430161Z_cdcnn_v6_9_epoch_aligned_full`) completed its five
`B0-stab-PS` checkpoints, then every `A1-aln-PS` attempt died during the second
CV fold with `terminate called after throwing an instance of 'c10::AcceleratorError'`,
raised while CUDA tensors were being destroyed. Both attempts of every seed
failed the same way.

The kernel log records the underlying cause:

```
NVRM: Xid (PCI:0000:01:00): 31, pid=8526, name=python,
      MMU Fault: ENGINE HOST0 HUBCLIENT_ESC faulted @ 0x2_06c07000.
      Fault is of type FAULT_PDE ACCESS_TYPE_VIRT_READ
```

Xid 31 is an illegal GPU memory access. After it, the driver refused every new
CUDA context on the machine: `nvidia-smi` still reported a healthy idle GPU,
because it needs no CUDA context, while `torch.zeros(4, device="cuda")` failed
with "CUDA unknown error" in every process, host venv and container alike. A
reboot cleared it.

## Suspected cause

The host virtual environment runs **torch 2.8.0+cu126** against driver
**535.309.01, a CUDA 12.2 driver**. That combination works only through CUDA
minor-version compatibility. The canonical 2026-09-11 run used
**torch 2.5.1+cu121**, which matches the driver's CUDA version, and trained for
hours without incident; the fault appeared during the first sustained run on the
newer stack.

This is a suspicion, not a proof. Reproducing it deliberately costs another
poisoned GPU and reboot, so it has not been attempted. The alternative
explanation is a transient driver or hardware fault that happened to land on the
new code path.

The epoch-alignment code is not implicated by the evidence available: the same
aligned stages — `A1-aln-PS`, `A2-lit-aln-PS`, `A3-lit-aln-PS` — run repeatedly
in one process inside the pinned container without faulting.

## Resolution: run training in the container

`docker/Dockerfile` pins the stack recorded by the canonical run: Python 3.11,
numpy 2.4.6, pandas 3.0.5, scipy 1.17.1, scikit-learn 1.9.0 and torch
2.5.1+cu121. The image holds no project code or data; the repository is mounted
at `/workspace`, so run directories, checkpoints and the immutable `Dataset/`
stay on the host.

```bash
docker build -t cdcnn:cu121 -f docker/Dockerfile .

docker run --rm -i --gpus all -v "$PWD":/workspace -w /workspace cdcnn:cu121 \
  python scripts/run_cdcnn_v6_full.py gpu-smoke --config configs/cdcnn_v6_9_epoch_aligned.json

docker run -d --gpus all -v "$PWD":/workspace -w /workspace cdcnn:cu121 \
  python scripts/run_cdcnn_v6_full.py launch --config configs/cdcnn_v6_9_epoch_aligned.json \
    --max-workers 1 --max-attempts 2 --gpu-smoke-run runs/<passing_gpu_smoke>
```

The base image is Bookworm rather than the canonical run's Bullseye, whose
security repository is archived, so the Python patch version differs. The
packages that determine training behaviour are pinned exactly.

## Consequence for comparisons

Runs are deterministic within one software environment, not across them. The
v6.4 to v6.8 results were produced on the host stack (torch 2.8.0+cu126); runs
from 2026-09-21 onwards use the container (torch 2.5.1+cu121). For that reason
the v6.9 ladder trains its own unaligned control, `A1-stab-PS`, alongside the
aligned stages, so the aligned-versus-unaligned comparison is made within a
single run rather than against the v6.6 numbers.

## Operational notes

- `nvidia-smi` is not a health check for CUDA. It reported an idle, healthy GPU
  throughout the outage. Use an allocation test:
  `python -c "import torch; torch.zeros(4, device='cuda')"`.
- A poisoned driver state fails every seed identically and instantly. Repeated
  identical failures across seeds indicate the machine, not the model.
- Recovery needs `sudo modprobe -r nvidia_uvm && sudo modprobe nvidia_uvm`, or a
  reboot.
